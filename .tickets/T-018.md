# Audio visualizer

A display page that reacts to whatever the PC is playing. It has several looks (bars, spectrogram, oscilloscope and others) and is picked like any other page in a profile.

## Architecture (decided by the existing design)

The display has no microphone, and the ESP32 should not do audio work. **The PC does the listening and the maths; the display only draws.** This is the same split as the System page (`{"t":"sys"}` lines).

```text
Windows audio output --WASAPI loopback--> service/aimon/audio.py
  --FFT, log bands, smoothing, peaks--> {"t":"aud",...} line at ~30 Hz over USB serial
  --> firmware parseAud -> viz.cpp renderer for the chosen mode
```

- **Capture:** WASAPI loopback of the default output device, so no "Stereo Mix" setup is needed. Candidates: `soundcard` (0.4.6, small, pure Python over WASAPI) or `PyAudioWPatch` (0.2.12.9, a PortAudio fork with loopback). Prototype `soundcard` first. `numpy` (2.2.5, installed) does the FFT.
- **Analysis on the PC:** 1024-sample Hann window at 48 kHz; about 32 log-spaced bands from 40 Hz to 16 kHz; dB scale mapped to 0-255 with automatic gain (a slow-decaying peak normaliser, so quiet and loud tracks both fill the screen); attack/decay smoothing; peak-hold values; 64 downsampled waveform points for the scope; RMS L/R for VU.
- **Bandwidth:** about 32 bands + 32 peaks + 64 scope points + 2 VU ≈ 130 bytes, hex-encoded ≈ 270 chars/line. At 30 Hz that is about 8 KB/s on a ~11.5 KB/s link (115200 baud). That is too close, so **send only what the current mode needs** (the firmware tells the service its mode with `@VIZ <mode>`, or the service reads it from the profile). It could also go to 230400 baud if the CH340 handles it reliably (test that first).
- **Silence:** after ~3 s below a threshold the service stops sending. The page fades to an idle look (slow drifting bars or the logo). It resumes instantly when sound returns.
- **Service only sends while the visualizer page is showing.** Otherwise it would spend CPU and serial bandwidth all the time. The firmware reports page changes (`@PAGE <id>`), or the service sends only after an `@VIZ on` from the firmware.
- **Frame rate:** scenes draw in 43-68 ms. Bars and the scope are much cheaper than parallax, so aim for 30 fps. Use 20 fps as the floor that still looks responsive.

## Modes (first pass)

| Mode | Look | Data |
|---|---|---|
| `bars` | Classic spectrum bars with falling peak caps | bands + peaks |
| `mirror` | Bars mirrored around the horizontal centre | bands |
| `spectrogram` | Scrolling waterfall: one new column per frame, colour = level (heat or theme palette) | bands |
| `scope` | Oscilloscope waveform line, optional glow trail | waveform |
| `radial` | Bars around a circle, pulsing on bass | bands |
| `vu` | Two analogue-style VU needles or LED meters (L/R) | VU |
| `mint` (later) | The Companion face reacts: mouth or eyes bounce to bass | bass level |

Shared options per mode: colour from a scene theme or palette (reuses the theme LUTs, so theme shift works too), band count (16/32), peak caps on/off, sensitivity.

The spectrogram scrolls the 8-bit frame buffer by one column (a memmove of 240 rows), which is cheap. It needs the canvas to persist between frames rather than being cleared.

## Profile and Studio

- New page `visualizer`, optionally `visualizer:<mode>` pages (like `scene:<id>`), plus a `visualizer` section in the profile with its mode, palette and options.
- An optional playlist-style "rotate modes every N seconds".
- Studio: a page card in Layout, and a mode picker with a live preview. The preview can use a recorded band stream, so no live audio is needed in the browser.
- Possible later "auto" behaviour: switch to the visualizer while music plays and return when it stops. **Needs an owner decision**, because it competes with the screensaver rules.

## Open questions for the owner

1. **Source:** all PC audio (loopback), or only a chosen app/device? Loopback of the default output is the simplest.
2. **Auto-switch:** should the display jump to the visualizer when music starts, or only show it when you navigate there?
3. **Which modes first?** Suggested MVP: `bars`, `spectrogram`, `scope`. `radial`, `vu` and `mint` would come later.
4. **Which profile?** Default (alongside Console/System/Parallax), the Dev profiles, or a new "Music" profile?

## Plan (tracer bullets)

1. **Spike (PC only):** loopback capture + FFT printing band levels; check latency and CPU (<3% target). Pick `soundcard` or `PyAudioWPatch`.
2. **Wire it end to end:** the `aud` line → firmware parse → `bars` mode on a new page, at 30 Hz. Measure frame time and the serial budget (`!PERF`), plus whether the usage/sys lines still arrive on time.
3. **Spectrogram and scope** modes with theme colours.
4. **Silence/idle handling**, plus sending only while the page shows.
5. **Profile, Studio** card, mode picker and recorded preview.
6. **Later modes:** radial, VU, MINT reacting. Optionally the auto-switch.

## Acceptance

- Music on the PC moves the bars within ~100 ms (by eye) at ≥20 fps on the display.
- The usage console still updates on time while the visualizer runs (no lost usage or sys lines).
- Silence goes idle within ~3 s, and the service sends no audio lines when the page is not showing.
- Each mode is selectable from a profile and the Studio.
