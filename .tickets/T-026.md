# Weather and daylight plan

Owner request (2026-10-28): a real weather API view, optional local-weather-driven parallax effects, and scene day/night lighting synchronized to local time/daylight. Planning only; no implementation or provider activation in this session.

## Scope and starting defaults

- Add an optional **Weather** page to the profile/navigation/Studio page registry. Keep Console as home; do not insert the page into the owner's current profile until implementation acceptance.
- At a glance: condition icon/description, temperature, feels-like, today's high/low, precipitation probability, wind, local time, data age and source attribution. Start with a compact next-hours forecast if it fits; multi-day detail is a later extension.
- Use the existing private configured latitude/longitude and IANA timezone as a shared default for brightness, weather and scene lighting. Introduce an explicit shared location setting/migration rather than silently depending on brightness being enabled. Location remains private; no automatic geolocation or credentials in profiles/screenshots.
- Preserve existing manual and random scene behavior. Add explicit playlist/scene weather modes: **Authored**, **Random**, **Local weather**, **Manual**. Daylight lighting separately chooses **Authored**, **Local daylight**, or **Manual phase**. These are proposed UI labels; settle final labels before coding.
- Propose Celsius and km/h for the initial Canadian setup, with selectable Fahrenheit/mph. Never mix configured units or precipitation amount with probability.

## Existing seams

- PC service already owns network collection and USB serial; firmware owns rendering. Weather fetches belong in a separately scheduled/cache-backed worker, never the frame loop, serial owner or quota refresh critical path.
- `service/aimon/brightness.py` already caches solar schedules and handles timezone/day rollover and polar conditions. Extract/reuse a shared daylight schedule through a small interface; keep backlight policy independently configurable. Do not fetch duplicate solar data from every scene or tie scene daylight to backlight duty.
- `firmware/AIUsageMonitor/ui.cpp` has random weather per playlist turn through `withWeather`, including clear/rain/snow/storm. Extend its source selection; do not mutate authored scene definitions or proliferate generated assets for every combination.
- Scene lighting should adjust sky, stars/sun and a controlled palette/light blend. A bright day is not merely maximum backlight; a dark night must preserve readable/recognizable artwork. Existing theme cycles remain usable when synchronization is off; avoid competing palette writers when it is on.

## Phased implementation

### A. Provider adapter and cached conditions

Define a provider-neutral snapshot: condition, temperature/feels-like, humidity where available, wind/gust/direction, precipitation amount/type/probability, high/low and short forecast; include source, valid time, fetched time, units, freshness/error, location identity. Mark provider-supplied current weather as modelled when applicable rather than claiming an on-site observation.

Candidate: [Open-Meteo forecast API](https://open-meteo.com/en/docs). Its current [terms](https://open-meteo.com/en/terms) restrict the free endpoint to noncommercial use and apply attribution/data-license requirements. Provider selection is **not final**: assess personal use versus commercial/client distribution, visible attribution and optional user-owned credentials before implementation. Do not market the free endpoint as unrestricted commercial infrastructure. No bundled key or silent paid subscription.

Propose weather refresh every 10 minutes, with one shared request/cache for all consumers, bounded timeout, jitter/backoff and in-flight deduplication. Proposed stale threshold 30 minutes and expired threshold 2 hours; make configurable, distinguish forecast valid time from fetch time. Daily solar schedules use the existing cache cadence. Quota/activity responsiveness must not regress during a slow weather request.

### B. Weather page

Add compact weather messages through the existing serial owner (field names/schema to be designed), bounded below firmware parser/buffer limits. Separate weather data age from USB link age. Known zero precipitation differs from unknown. Failed requests retain last measured values with stale/age status; expired/absent data is visibly unavailable. Show a human-readable provider credit/link on Weather and in Studio/status as required by the selected source.

Use project-drawn weather icons or separately verified licensed icons; add any third-party terms to the inventory. No unverified weather artwork or font download. Weather page save/build/reload and touch navigation must match existing profile behavior.

### C. Local weather effects

Map provider conditions deterministically: rain/showers -> rain, snow -> snow, thunderstorm -> storm, dry -> clear/cloudy. Define drizzle, freezing rain, mixed precipitation, fog and unknown explicitly; unsupported effects use a documented approximation rather than a false measurement. Temperature alone must not imply snow. Optional light/medium/heavy mapping uses reported precipitation, with bounds and hysteresis.

Crossfade/blend effects and change at safe boundaries to avoid abrupt resets or flickering. Retain only compatible authored effects; e.g. stars follow daylight while authored rain is replaced in Local weather mode. Do not add lightning to every rainy condition. On expired/unknown weather, use an explicitly selected authored/manual fallback; do not silently substitute random weather or claim it reflects local conditions.

### D. Daylight synchronization and Studio controls

Derive dawn/day/dusk/night and a smooth blend from local time plus valid solar events, reusing the solar cache even while weather is offline. Twilight can use provider dawn/dusk when supplied or a clearly defined transition around sunrise/sunset. Recompute at timezone/date changes, DST transitions, clock adjustments and location changes. Handle polar day/night; never invent a sunrise. Monotonic device interpolation should continue between service messages; bound validity and freeze/fallback safely on stale time/location data.

Studio exposes source/mode, location/units, cadence/freshness, manual weather/phase and preview overrides. Preview overrides are explicitly synthetic and must not overwrite provider caches. Changes must indicate whether they apply live or require service restart/build. An independent daylight toggle leaves backlight behavior intact. No scene/weather update should wake the usage dashboard or replace the user's selected page.

## Proposed acceptance for the owner's testing phase

- Fixture coverage of every supported condition, zero/unknown values, units, stale/expired responses and backoff; no network in tests.
- Same cached conditions feed Weather and scenes; simulate slow API/offline/reconnect without blocking quota updates or serial ACKs.
- Sunrise/sunset boundary, midnight, DST, wrong/missing timezone, location change, clock rollback and polar day/night cases.
- Manual/authored/random/local weather and independent daylight combinations survive save/reload/build and remain compatible with theme cycles when sync is off.
- Device/framebuffer evidence: Weather day/night, clear/rain/snow/storm parallax, dawn/dusk blends; inspect readability and transitions. Check frame pacing, RAM/flash and serial bandwidth; no full-frame network/serial data.
- Provider attribution, exact terms, privacy and icon/asset licenses verified before public release. No secrets/location in fixtures, screenshots or Git.

## Implementation gates

Deliver A/B first, then C/D; split into bounded implementation tickets with explicit paths and acceptance commands when scheduled. Existing future-feature backlog remains intact.
