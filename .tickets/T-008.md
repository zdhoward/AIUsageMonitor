# Implementation planning brief

**Purpose:** Give Sol 6.1 a concrete, reviewable product request to refine into implementation tickets. This records the owner's requested behavior and desired outcomes. It is not authorization to implement, a final architecture decision, or a promise that all stages belong in one release.

## Product goal

Make the monitor's display extensible with optional, enjoyable visual pages while preserving its core quota dashboard and reliable PC-to-device telemetry. Owners should be able to enable/disable pages and choose which page appears as a screensaver through a simple build-time configuration file. No clickable settings page is wanted.

The default page list should include every available page, active and navigable, including a Screensaver page/entry. The screensaver behavior itself is disabled by default. When enabled, it shows a build-configured available page after inactivity; a tap wakes to the view that was active before the screensaver and does not advance navigation. Sol should preserve the Screensaver entry in the default page list while deciding with the implementer how direct navigation to that entry relates to the selected screensaver target.

## Current baseline and constraints

- Main checkout firmware currently documents Console and Details as the two views. Earlier optional-page work is represented by T-001 and a test/flash branch; verify the target branch and actual device baseline before implementation.
- The ESP32-2432S024C has a 320×240 landscape display, no PSRAM reported on the tested board, and a single 76,800-byte 8-bit RGB332 framebuffer.
- The existing PC service owns the USB serial connection and sends newline-delimited JSON payloads. Do not create a second process that competes for the device's COM port or introduce the sample's bare `CPU,RAM` line protocol. Any companion state must be integrated with the existing PC service/device protocol.
- Firmware owns drawing and touch/navigation. Keep the existing quota and data-source behavior intact.
- 16-bit full-frame buffers use 115,200 bytes at 240×240 or 153,600 bytes at 320×240. At the configured 40 MHz SPI clock, sending one 320×240 RGB565 frame has a 30.72 ms theoretical lower bound before overhead, so sample claims of 30–40 FPS need on-device measurement.
- Research on asset authoring and procedural scenes is in [IMAGE_ANIMATION_RESEARCH.md](../docs/IMAGE_ANIMATION_RESEARCH.md). Its figures and proposals are not runtime proof or locked design.

## Requested capabilities

### 1. Simple build-time page configuration

Provide one approachable configuration file to control which pages are compiled, visible/navigable, and eligible as screensaver content, plus screensaver enablement and selected page. Keep build-time configuration; do not add an on-device settings page. Defaults: every available page, including the Screensaver page/entry, is included and navigable; screensaver activation is off. Invalid combinations should be caught clearly during build or startup rather than silently selecting an unavailable page.

The existing Console and Details remain available. Retain the Companion placeholder (a simple face looping between idle and happy) and Images placeholder (centered text describing the future image/animation page) until replaced by their fuller versions. Keep optional features easy to disable.

### 2. Screensaver behavior

After configured inactivity, render the selected enabled page as a screensaver. The page can be any suitable enabled page, including the companion, image/animation player, or a procedural scene. A valid tap wakes to the exact previous view without consuming a navigation step. Normal page cycling, disabled mode, and telemetry rendering continue to work. Screensaver stays disabled in the default config.

### 3. MINT digital pet, with PC-side behavior

Create an original, small retro-electronic robot character named MINT. The PC service should do the thinking: mood/personality, idle-expression choice, response to interactions, and optional CPU/RAM awareness. The ESP32 should receive concise state/animation information and render it. Do not duplicate the personality or telemetry logic in firmware.

The desired feel includes a bounded mood that changes gradually, weighted idle expressions, independent non-blocking blink/eye/breathing animation, and temporary reactions such as pet/play/nap. CPU or RAM reaching about 80% may trigger a worried/sweating expression; clear the alert below about 75% to avoid flicker. Use fresh telemetry only; stale/missing PC data must not leave MINT permanently stressed. These values are initial product guidance for Sol/implementation review, not a finalized tuning contract. PC awareness should be optional and must not require credentials, prompts, transcripts, or new provider requests.

The PC service already has exclusive serial ownership and a JSON protocol. Extend that path for companion state and interactions if needed; settle message shape, cadence, compatibility, and stale-data behavior during implementation design. No separate `mint_pc_bridge.py` process should open the same serial port.

### 4. Procedural visual scenes

Add optional procedural pages using the existing renderer/lifecycle where practical. Candidate scenes:

- **Starfield:** perspective stars flying outward from a vanishing point.
- **Tiny living world:** synthwave sunset, layered skyline, moving pod, rain, and neon road.
- **Ambient liquid:** spring-like surface ripples, occasional droplets and splashes, gradual filling, then a self-drain/flush cycle when liquid reaches roughly 80% of screen height; repeat calmly.

The supplied liquid sample does not implement gradual fill or flushing; those are explicit desired additions. For planning, “80%” means liquid covers roughly 80% of the screen from the bottom, then drains close to empty. Sol should check whether that interpretation should be confirmed before implementation. Keep the liquid simulation lightweight; a full 2D fluid simulation is not a requirement. Build-time config determines which scenes are included/available; enabled pages are normally navigable and may be selected as the screensaver.

Treat 30–40 FPS in sample sketches as unverified targets. Measure frame duration, heap, and responsiveness on the actual board, and tune complexity and animation rate accordingly. Preserve responsive quota pages and touch wake behavior.

### 5. Image and animation page and asset workflow

Initially keep a friendly placeholder page. Plan an authoring/conversion path that lets creators work with individually named frames and metadata rather than manually calculating sprite-sheet coordinates. A host-side tool should validate/order source frames and produce compact firmware-ready assets. Static images can be treated as a one-frame animation. GIF, PNG sequences, metadata-mapped sprite sheets/Aseprite exports, and procedural animation are candidate sources, with implementation order and supported formats left to the implementer/review.

Keep runtime playback simple for the ESP32; preserve editable source artwork. Plan for frame timing, loop behavior, positioning/anchor, transparency, and named animation states as appropriate. Choose pixel format, asset packaging, limits, and converter integration only after measuring flash/heap and confirming the existing renderer can support them. Do not introduce LVGL or external storage solely by assumption.

## Suggested delivery slices

Sol 6.1 should challenge the order, split, dependencies, and acceptance criteria before implementation. A reasonable starting sequence is:

1. **Configuration and page lifecycle:** establish the default-on page list, build-time enable/disable behavior, navigation, and disabled-by-default screensaver with wake-to-prior-view. Confirm actual target branch/device baseline first.
2. **MINT vertical slice:** render the original pet, connect PC-side state through the existing protocol, implement idle/reaction/alert behavior on the PC, and verify stale/disconnected handling. Keep the Companion page and PC feature optional.
3. **Procedural scene vertical slice:** add one modest scene first, measure on device, then add the other scenes and liquid fill/flush behavior if performance and memory allow. Avoid implementing three heavy renderers before learning the board's limits.
4. **Image/animation pipeline:** preserve placeholder behavior while defining one minimal end-to-end converter and player path; add additional import formats only after the basic path is validated.
5. **Integration and handoff:** verify configuration variants, navigation, screensaver wake/return, existing dashboard/service behavior, device resource use, and framebuffer evidence. Update setup/UI/protocol/research docs and record unresolved hardware checks.

These slices are a planning aid, not a promise to bundle every capability in a single release. Each implementation slice should have its own bounded ticket and report files changed, checks run, device evidence, limitations, and follow-up work.

## Completion criteria for the overall effort

- Build-time configuration is understandable and defaults to all available pages, including the Screensaver page/entry, enabled/navigable, with screensaver activation disabled.
- Screensaver selection is constrained to an available page; inactivity activation and tap-to-prior-view wake are correct.
- Console/Details and PC collection behavior remain intact.
- MINT behavior is computed on the PC service and drawn on-device; optional system metrics and stale/disconnect behavior are safe and visible.
- Procedural scenes and the liquid fill/flush cycle operate within measured board limits, with their optional pages configurable.
- The Images placeholder remains useful until a documented asset-conversion/playback path replaces it; supported inputs and asset limits are documented.
- Production firmware builds and affected service checks pass at sprint end; on-device framebuffer evidence covers each completed visual slice. Do not claim physical touch or runtime performance without evidence.
- Documentation and project log match the shipped behavior; no unrelated telemetry data-source changes or credentials are introduced.

## Owner choices already established

- Screensaver behavior defaults off; page availability defaults to all pages on.
- The default page list includes a Screensaver page/entry; when screensaver behavior is configured, its displayed content can be selected from available pages.
- Tap wakes to the previous view.
- Companion placeholder loops idle/happy; image page starts as centered explanatory text.
- Settings are build-time, not clickable on the device.
- The PC should make MINT's behavioral decisions and send display state; ESP32 renders it.
- The concepts and supplied sketches are inputs for review, not mandates to copy code or make unreviewed technical decisions.
